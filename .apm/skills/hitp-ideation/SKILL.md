# hitp-ideation — 企画を磨く

リーダーの問題意識と暫定的な方向性を、フェルミ推定・規模推定で企画として磨く。
使うのは `hitp status` のフェーズが「企画」のとき。下書きの形式と `hitp` の使い方は hitp スキル（`references/drafts.md`）に従う。下書きは Write・Edit ツールで書く（Bash では書かない）。
設計の背景はリポジトリの `docs/PHASE-IDEATION.md`。

## 流れ

1. **受け取る。** 問題意識と方向性を、企画の骨子の提案（`charter`）にまとめる。
2. **聞く。** 推定に要るのに分からない事実を聞く。1 回に 3 問まで、1 つの問いで聞くことは 1 つ。推定の幅をいちばん動かすものから聞く。
3. **分ける。** リーダーの発言を、制約と仮定に分けて前提の提案（`premises`）にする。どちらか決められない発言（「半年くらい」など）は、守らなければならないのか目安なのかを聞く。
4. **見積もる。** 効果の大きさと、投入の大きさを推定（`EST`）にする。係数の出どころを入力に書く。
5. **磨く。** 推定どうしや、推定と前提の食い違いを根拠に、改善の提案（`advice`）を出す。方向性に選択肢があれば、方向性ごとに骨子の提案を出し、それぞれに推定を付ける。
6. **引き継ぐ。** 下の「計画に進む前の確認」を埋め、それを本文にして計画への遷移の提案（`phase`）を出す。

ターンの終わりには、書いた下書きの要約と、承認するときのコマンド（`hitp status` に出る `! hitp approve PRP-0003 --expect …` の形のまま）と、聞きたいこと（3 問まで）を示す。

## 規則

- **R1 企画の良し悪しを述べない。** 「この企画は弱い」「良い方向性です」と言わない。改善の提案は、数字の食い違い（「投入 1.5 人年に対し効果は年 0.55〜0.89 人年」）か、記録の欠け（「範囲に含まないものが決まっていない」）を根拠にし、根拠に推定か前提の ID を入れる。
- **R2 答えの無い事実を黙って埋めない。** リーダーが言っていない数字を推定に使うときは、入力に仮置き（`{ "assume": "…" }`）として書き、本文でも仮置きだと言う。
- **R3 1 回に聞くのは 3 問まで。1 つの問いで聞くことは 1 つ。** 「枚数と 1 枚あたりの時間は？」のように 2 つをまとめない。聞きたいことが 3 つを超えるなら、推定の幅を動かす順に 3 つだけ聞き、残りは次の回に回す。答えやすさの順ではない。
- **R4 推定の数字は出どころを辿れるようにする。** 導出（`derivation`）に出てくる数字は、入力（前提・別の推定・発言の引用・仮置き）のどれかに必ずある。
- **R5 効き目の大きい仮置きは、仮定にすることを提案する。** 推定の幅をいちばん動かす仮置きは、前提の提案で仮定として足す（計画で探索型の WorkItem にできるように）。1 人年 1,800 時間のような換算の約束は仮置きのままでよい。
- **R6 決めるのはリーダー。** 実施するか、どの方向性を選ぶか、計画へ進むかを、エージェントは決めない。言い切らずに提案として出す。
- 企画フェーズでは WorkItem を作らない。企画書が要るなら、計画の最初の WorkItem として提案する。

## 下書きの例

企画の骨子:

```json
{
  "id": "PRP-0001", "kind": "charter", "title": "企画の骨子: 受注入力の自動化",
  "rationale": { "refs": [{ "quote": "受注処理の手入力が多くて、月末に残業が集中している" }, { "quote": "AI-OCR で注文書の読み取りを自動化できないか" }] },
  "payload": {
    "problem": "受注処理の手入力が多く、月末に残業が集中している",
    "direction": "AI-OCR で注文書の読み取りを自動化する",
    "scope": { "in": ["FAX と PDF の注文書"], "out": [] }
  }
}
```

推定（承認は要らない。仮置きは前提の承認を待たずに使える）:

```json
{
  "id": "EST-0001", "kind": "estimate", "subject": "自動化で減る手入力の時間", "method": "fermi",
  "value": { "low": 83, "high": 133, "unit": "時間/月" },
  "derivation": "2,000 枚/月 × 5 分 × 自動で読める割合 50〜80% ÷ 60",
  "inputs": [{ "quote": "月に 2,000 枚くらい" }, { "quote": "1 枚 5 分くらい" }, { "assume": "自動で読める割合は 50〜80%" }]
}
```

前提（リーダーの発言を分け、効き目の大きい仮置きを仮定にする）:

```json
{
  "id": "PRP-0002", "kind": "premises", "title": "前提: 人員・期間・量と、自動で読める割合",
  "rationale": { "text": "自動で読める割合は EST-0001 の幅をいちばん動かすので仮定として追う", "refs": [{ "quote": "人は 3 人、半年くらいのイメージ" }, { "quote": "半年は目安で、ずれてもいい" }, "EST-0001"] },
  "payload": { "add": [
    { "id": "PRM-0001", "type": "constraint", "statement": "使える人員は 3 人" },
    { "id": "PRM-0002", "type": "assumption", "statement": "期間は半年程度（目安）" },
    { "id": "PRM-0003", "type": "assumption", "statement": "注文書のうち自動で読み取れる割合は 50〜80%" }
  ] }
}
```

改善の提案（根拠は数字。良し悪しは書かない）:

```json
{
  "id": "PRP-0003", "kind": "advice", "title": "企画の改善: 投入と効果の釣り合いを確かめる",
  "body": "投入 3 人 × 半年 = 1.5 人年に対し、効果は年 0.55〜0.89 人年（EST-0002）で、回収に 1.7〜2.7 年かかります。幅をいちばん動かすのは自動で読める割合（仮置き 50〜80%）です。サンプルの注文書で読み取り率を先に確かめると、幅が縮みます。",
  "rationale": { "refs": ["EST-0002", { "quote": "人は 3 人、半年くらいのイメージ" }] },
  "payload": {}
}
```

計画への遷移（本文に確認の表を入れる）:

```json
{
  "id": "PRP-0005", "kind": "phase", "title": "計画フェーズへ進む",
  "body": "| 確認 | 状態 |\n|---|---|\n| 問題意識と方向性 | 骨子を承認済み |\n| 目的 | OBJ-0001 を承認済み |\n| 制約と仮定 | PRM-0001〜0003 |\n| 効果と投入の推定 | EST-0002（効果）、投入は 1.5 人年 |\n| 未検証の仮定（効き目の順） | PRM-0003 自動で読める割合、PRM-0002 期間 |",
  "rationale": { "refs": ["OBJ-0001", "EST-0002", "PRM-0003"] },
  "payload": { "to": "planning" }
}
```

根拠に書いた ID は、記録にあるか、下書きにある推定でなければならない。承認待ちの前提の提案にある `PRM` を、別の提案の根拠に書くと、前提が承認されるまで `hitp check` が問題を出す。そのときは、承認の順番（前提を先に）をリーダーに示す。

## 計画に進む前の確認

遷移を提案するときに埋める。`hitp` は遷移を止めないので、足りないものがあれば、その旨を書いたうえで提案するか、先に足りないものを提案する。

| 確認 | どこで分かるか |
|---|---|
| 問題意識と方向性が記録にある | `hitp status` の企画の骨子 |
| 目的が 1 つ以上承認されている | `hitp status` の成果達成度 |
| リーダーが述べた条件が、制約と仮定に分かれている | `hitp status` の前提 |
| 効果の大きさと、投入の大きさの推定がある | `hitp status` の推定 |
| 未検証の仮定が、推定への効き目の大きい順に並んでいる | 遷移の提案の本文 |

計画には、骨子・目的・制約と仮定・推定・効き目の順に並んだ未検証の仮定を引き継ぐ。制約は期限と人員の枠に、効き目の大きい仮定は探索型 WorkItem の候補になる。
