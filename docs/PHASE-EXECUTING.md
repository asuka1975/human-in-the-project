# 推進フェーズの振る舞い

推進フェーズで、エージェントが何をどの順で行い、何を記録に残すかの設計。
スキルは `.apm/skills/hitp-executing/SKILL.md`。

## 推進でやること

要件: 「人間側の報告や成果物の提出を受けて、プロジェクトの進捗を管理し、メンバーへの進捗確認を提案します。また、不測の事態が起こったときには計画の合理的判断に基づき修正を提案します」。

| | 中身 |
|---|---|
| 受け取るもの | リーダーの進捗報告（メンバーの報告もリーダー経由）、不測の事態、成果物の提出、完了報告 |
| 出すもの | 進捗報告・不測の事態・完了報告の記録の下書き、提出のコマンドの組み立て、進捗確認の依頼の提案、仮定の検証状態と目的の達成状況の提案、再計画の提案（修正案 2〜3 個）、終了への遷移の提案 |
| しないこと | 作業の完了を宣言する。メンバーに直接連絡する。成果物の良し悪しを述べる。人を評価する。仮説の棄却を失敗と呼ぶ |

## 流れ

1. **受け取る。** リーダーの報告を、進捗報告・不測の事態・完了報告の下書きにする。チェックポイントを通過したという報告なら、`! hitp checkpoint <WI> <番号>` を示す（下書きは要らない）。成果物が揃ったら、リーダーの言葉（誰が・いつ・結果）から提出のコマンドを組み立てて示す。
2. **見る。** `hitp status` で、見通し・最近の報告・棄却された仮定のあとに来る WorkItem を見る。
3. **確かめる。** 報告が途絶えている進行中の WorkItem があれば、進捗確認の依頼をリーダーへの提案（`advice`）にする。
4. **読む。** 提出された成果物を読み、計画上の事実（例: 読み取り率 42%）を取り出す。探索型の WorkItem の成果物なら、確かめた仮定の検証状態の提案（`assumption-status`）を出す。
5. **直す。** 見通しが期限を超えた、不測の事態が起きた、仮定が棄却された、のどれかなら、影響を `hitp` の数字で示し、再計画の修正案を 2〜3 個出す（`replaces` は今の計画）。目的の達成状況が変わるなら、その提案も出す。
6. **閉じる。** 下の「終了する前の確認」を根拠に、終了への遷移を提案する。

## スキルに書く規則

| # | 規則 | 理由 |
|---|---|---|
| E1 | 完了を宣言しない。成果物を生む WorkItem はリーダーの提出でだけ、生まない WorkItem は完了報告の承認でだけ完了する。提出のコマンドのゲートの記録（誰が・いつ・結果）は、リーダーの言葉から取り、作らない | INV-1・INV-5・INV-10 |
| E2 | 進捗確認は、リーダーへの提案にする。メンバーに連絡しない | INV-8 |
| E3 | 不測の事態は、記録の下書きにし、見通しへの影響を `hitp` の数字で示す。期限を超えるなら修正案を 2〜3 個出す | 「計画の合理的判断に基づき修正を提案」。計画の P2・P3 と同じ |
| E4 | 成果物を読んで事実を取り出すのはよいが、良し悪しは述べない（「報告が雑」「検証が甘い」と書かない） | INV-9 |
| E5 | 仮説の棄却を失敗と呼ばない。不確実性の解消として扱い、計画と目的への影響を数字で示す | R&D の 3 軸。作業進捗と不確実性の解消度は進み、成果達成度は進まないことがある |
| E6 | 人を評価しない。遅れは「最後の報告から 7 営業日」「残り 10〜15 人日」のように事実で書く | 計画の P5 と同じ |
| E7 | 目的の達成状況の提案は、成果物や報告の事実を根拠にする | 成果達成度はリーダーの入力（DOMAIN-MODEL） |

## 例（2026-10-13 に、当時の `hitp` で通したもの）

計画スキルの例の続き。計画は WI-0001 読み取り率の検証（鈴木、探索、仮定「自動で読める割合は 50〜80%」を確かめる）→ WI-0002 OCR 連携の実装（田中）→ WI-0003 試行運用（佐藤）、期限 2027-02-26。

| 日付 | 起きたこと | 今の `hitp` で起きたこと |
|---|---|---|
| 11/09 | 鈴木さんの報告「200 枚のうち 120 枚を読み取った。残りは 1〜2 日」 | 進捗報告として記録できた。WI-0001 が進行中になった。**見通しは「上限で 3 営業日超える」になった**。進行中の WorkItem を推定の全量（4〜8 人日）で数えるため。残り 1〜2 人日で数えれば 37〜68 営業日で、期限まで 80 営業日に収まる |
| 11/18 | 不測の事態「田中さんが 11/30 から 2 週間、別案件の応援に入る」 | 不測の事態として記録できた。**見通しは変わらなかった**。不在を表す方法が無い。11/20 の見通しは 34〜63 営業日／71 営業日だが、実装が 10 営業日止まるので、実際は 44〜73 営業日で上限が期限を超える |
| 11/20 | 検証報告を提出（課内の発表は課長が 11/19 に通過）。報告には「全体 42%（FAX 20%、PDF 64%）」 | 提出できた。エージェントは成果物を読み、仮定の検証状態の提案（棄却、根拠 DLV-0001）を書けた。**棄却の仮定のあとに来る WI-0002 は「未着手」と出るだけ**で、見直しが要ることはどこにも出ない |
| — | 進捗確認のきっかけ | **最後の報告がいつかは `status` に出ない**。`hitp show WI-0001` で報告の一覧を見るしかない。不測の事態も `status` に出ない |

探索型の WorkItem の「結論」（支持・棄却・未決）は、DOMAIN-MODEL には書いたが実装していなかった。例では、確かめた仮定の検証状態（棄却、覚え書き「全体 42%」）で足りた。

### 当時の形式で足りなかったところ

1. **進捗が見通しに入らない。** 進捗報告は文章だけで、残りの工数を持たない。時間がたつほど、見通しは進行中の作業を全量で数え、ありもしない遅れを出す。
2. **不在が見通しに入らない。** メンバーの稼働は 1 つの数で、期間を区切った不在（応援・休暇）を表せない。
3. **棄却された仮定のあとに来る作業が目立たない。** 再計画のきっかけとして、いちばん大事なものが見えない。
4. **最近の報告と不測の事態が `status` に出ない。** 報告が途絶えた作業を見つけられない。

## 終了する前の確認

| 確認 | どこで分かるか |
|---|---|
| すべての WorkItem が完了か中止 | `hitp status` の WorkItem |
| 目的ごとの達成状況が、事実を根拠に更新されている | `hitp status` の成果達成度 |
| 未検証の仮定が残っていれば、その扱い（検証しないまま閉じる理由）が本文に書いてある | `hitp status` の不確実性の解消度 |
| 不測の事態のそれぞれが、再計画か「影響なし」の判断につながっている | 決定の記録 |

## 決めたこと

2026-10-13 に、すべて推奨どおりで承認された。1 には、リーダーの言葉「WorkItem の中にチェックポイントを作った上で人間側が今このチェックポイントをクリアしたと報告しやすくしてほしい」が加わった。計画の WorkItem にチェックポイント（区切りと、通過後に残る工数）を置き、リーダーは `hitp checkpoint <WI> <番号>` の 1 行で通過を記録できる。

| # | 決めること | 推奨（採用） | 代案 |
|---|---|---|---|
| 1 | 進捗の数字 | 進捗報告に残りの工数（`remaining`、人日の下限〜上限。省ける）を持たせる。見通しは、進行中の WorkItem を最新の報告の残りで数える | 進み具合の割合（%）を持たせる。見通しは今のまま全量で数える |
| 2 | 不在の期間 | メンバーに不在の期間（`away`: 開始日〜終了日の並び）を持たせる。見通しは、その担当者の不在の営業日を飛ばして数える。不測の事態のあと、エージェントがメンバーの更新を提案する | 不在を、担当者の稼働の一時的な変更として扱う（変えて戻す提案を 2 回出す） |
| 3 | 棄却された仮定のあとに来る作業 | `status` に「見直しが要るもの」を出す: 未完了の WorkItem のうち、棄却された仮定を確かめた探索型の WorkItem に（たどって）依存するもの。`hitp` は止めず、エージェントが再計画を提案するきっかけにする | 出さない（エージェントが記録を読んで気づく） |
| 4 | 探索型の結論 | WorkItem に結論の項目は作らない。結論は、確かめた仮定の検証状態（支持・棄却、未決は未検証のまま覚え書き）で表す。DOMAIN-MODEL の書き方を直す | WorkItem に結論を持たせ、提出か完了報告のときに記録する |
| 5 | `status` の表示 | 最近の進捗報告と不測の事態（新しい順に数件）と、進行中の WorkItem ごとの「最後の報告からの営業日」を出す | — |
| 6 | 進捗確認を提案する目安 | 進行中の WorkItem で、最後の報告から 5 営業日を超えたら、進捗確認の依頼をリーダーに提案する。リーダーが別の目安を言えば、それに従う | 目安を決めない |
| 7 | 終了の条件 | 上の確認の表をスキルに置き、`hitp` は止めない（企画・計画と同じ） | `hitp` が、未完了の WorkItem が残る終了を止める |
| 8 | 規則 E1〜E7 | 上のとおり | — |
