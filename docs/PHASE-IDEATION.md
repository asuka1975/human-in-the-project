# 企画フェーズの振る舞い

企画フェーズで、エージェントが何をどの順で行い、何を記録に残すかの設計。
スキルは `.apm/skills/hitp-ideation/SKILL.md`。

## 企画でやること

要件: 「人間が考えた問題意識や暫定的な方向性をベースとして、フェルミ推定やスケール推定を行いながら企画として磨きます」。

| | 中身 |
|---|---|
| 受け取るもの | リーダーの問題意識と、暫定的な方向性 |
| 出すもの | 企画の骨子の提案、目的の提案、前提（制約・仮定）の提案、推定（フェルミ推定・規模推定）、企画の改善の提案、方向性の選択肢 |
| しないこと | 企画の良し悪しを述べる。実施するかを決める。答えの無い事実を黙って推測で埋める |

## 流れ

1. **受け取る。** 問題意識と方向性を骨子の下書きにまとめる。
2. **聞く。** 推定に要るのに分からない事実を、1 回に 3 問まで聞く。1 つの問いで聞くことは 1 つ。推定の幅をいちばん動かすものから聞く。
3. **分ける。** リーダーの発言を制約と仮定に分ける。どちらか決められない発言（「半年くらい」など）は、どちらかを聞く。
4. **見積もる。** 効果の大きさと、投入の大きさを推定する。係数は、リーダーの発言・記録にある前提・エージェントの仮置きのどれかから取り、出どころを残す。
5. **磨く。** 推定どうしや、推定と前提の食い違いを根拠に、改善を提案する（例: 投入に対して効果が小さい、制約と衝突する、幅が広すぎて判断に使えない）。方向性の選択肢を 2〜3 個示し、それぞれに推定を付ける。
6. **引き継ぐ。** 下の「計画に進む前の確認」を根拠に、計画フェーズへの遷移を提案する。決めるのはリーダー。

## スキルに書く規則

| # | 規則 | 理由 |
|---|---|---|
| R1 | 企画の良し悪しを述べない。改善の提案は、数字の食い違いか記録の欠けを根拠にする（「この企画は弱い」ではなく「効果 0.55〜0.89 人年/年に対し投入 1.5 人年」） | INV-9 は成果物についての規則だが、「磨く」は評価の言葉を誘う。根拠の参照（INV-7）を数字に限ると線が引ける |
| R2 | 答えの無い事実を黙って埋めない。埋めるときは仮置きか仮定として明示する | 推測で埋めると、決まっていないことが決まったように扱われる |
| R3 | 1 回に聞くのは 3 問まで。1 つの問いで聞くことは 1 つ。推定の幅を動かす順に聞く | ヒアリングが尋問にならないように。1 つの問いに複数を詰めると、数の上限が効かなくなる（試したときに起きた。2026-10-13 に追加）。答えやすいものから聞くと、推定に効かない問いが先に来る |
| R4 | 推定の数字は、すべて出どころ（発言の引用・前提・仮置き・別の推定）を辿れるようにする | INV-6。フェルミ推定は結果より導出に価値がある（PLAN §3①） |
| R5 | 推定の幅をいちばん動かす仮置きは、仮定として前提に足すことを提案する | 仮定になれば不確実性の解消度で追え、計画で探索型 WorkItem にできる（R&D の軸） |
| R6 | 実施するか、どの方向性を選ぶか、計画へ進むかはリーダーが決める | PLAN §2「プロジェクトの実施を独断で決定」しない |

## 例（2026-10-13 に、当時の `hitp` で通したもの）

リーダー:
> 受注処理の手入力が多くて、月末に残業が集中している。AI-OCR で注文書の読み取りを自動化できないか。人は 3 人、半年くらいのイメージ。

エージェントが聞く（3 問、推定を動かす順）:
1. 注文書は月に何枚くらいですか。
2. 1 枚の手入力に何分くらいかかっていますか。
3. 「半年」は守らなければならない期限ですか、目安ですか。

リーダー:
> 月に 2,000 枚くらい。1 枚 5 分くらい。半年は目安で、ずれてもいい。注文書の形式は FAX と PDF が混ざっていて割合は分からない。

エージェントの下書き:

| ID | 中身 |
|---|---|
| 前提の提案 | 制約: 使える人員は 3 人。仮定: 期間は半年程度（目安）、注文書は月 2,000 枚、1 枚 5 分 |
| EST-0001（フェルミ推定） | 減る手入力の時間 = 2,000 枚/月 × 5 分 × 自動で読める割合 50〜80% ÷ 60 = **83〜133 時間/月** |
| EST-0002（規模推定） | 効果 = EST-0001 × 12 か月 ÷ 1,800 時間/人年 = **0.55〜0.89 人年/年** |
| 改善の提案（`advice`） | 投入 3 人 × 半年 = 1.5 人年に対し、効果は年 0.55〜0.89 人年。回収に 1.7〜2.7 年。幅をいちばん動かすのは自動で読める割合で、ここは誰も数字を持っていない |
| 目的の提案 | 受注処理の手入力の時間を月 80 時間以上減らす |
| フェーズ遷移の提案 | 計画へ |

「半年は目安」の答えで、期間は制約ではなく仮定に入る。「自動で読める割合 50〜80%」と「1,800 時間/人年」はリーダーが言っていない、エージェントの仮置き。

### 実際に通して分かった、当時の形式で足りなかったところ

1. **問題意識の置き場が無い。** 「月末に残業が集中している」は、目的の提案の根拠の引用の中にしか残らなかった。プロジェクトが持つのは名前だけで、目的は「達成したいこと」であって「なぜ」ではない。推定が何の大きさを測っているのかの錨も無い。
2. **仮置きの係数を、推定に正直に書けない。** 推定の入力は、記録にある前提か、リーダーの発言の引用だけを受け付ける。仮置きの「50〜80%」を入力にするには、先に前提の提案としてリーダーに承認してもらうしかない。実際、前提が承認されるまで、推定 2 件・改善の提案・目的の提案・遷移の提案のすべてで、`hitp check` が「PRM-0003 が見つかりません」などを出した（問題 19 件のうち 18 件が前提の承認待ち）。前提の提案を 2 つ承認して、やっと消えた。リーダーは、仮置きがどんな数字を生むかを見る前に、それをプロジェクトの仮定として承認することになる。推定は承認不要と決めた（`STORAGE.md`「設計の判断」4）のに、入力を通して承認が要ることになっている。
3. **承認した推定が一覧で見えない。** 改善の提案の承認で推定 2 件が記録に写ったが、`hitp status` には出ず、`hitp show EST-0001` で 1 件ずつ見るしかない（前提の一覧を足す前と同じ状態）。

## 計画に進む前の確認

エージェントは、遷移を提案するときにこの表を埋めて根拠にする。`hitp` は遷移を止めない（フェーズでコマンドを制限しない、と決めたため）。

| 確認 | どこで分かるか |
|---|---|
| 問題意識と方向性が記録にある | `status` の企画の骨子 |
| 目的が 1 つ以上承認されている | `status` の成果達成度 |
| リーダーが述べた条件が、制約と仮定に分かれている | `status` の前提 |
| 効果の大きさと、投入の大きさの推定がある | 推定 |
| 未検証の仮定が、推定への効き目の大きい順に並んでいる | 遷移の提案の本文 |

## 計画に引き継ぐもの

骨子、承認された目的、制約と仮定、推定、効き目の順に並んだ未検証の仮定。計画では、制約が期限と人員の枠になり、効き目の大きい仮定が探索型 WorkItem の候補になる。

## 決めたこと

2026-10-13 に、すべて推奨どおりで承認された。

| # | 決めること | 推奨（採用） | 代案 |
|---|---|---|---|
| 1 | 問題意識・方向性・範囲の置き場 | 企画の骨子という提案の種類（`charter`）を足す。中身は問題意識・方向性・範囲（含むもの・含まないもの）。承認すると置き換わり、`status` に出る | 置き場を作らず、目的と根拠の引用で済ませる |
| 2 | 推定に使う仮置きの係数 | **B: 推定の入力に「仮置き」（`{ "assume": "…" }`）を許す。** 推定は書いた時点で検査を通る。効き目の大きい仮置きは、仮定として前提に足すことを提案する（R5）。INV-6 の「入力の Premise」を「入力（前提・発言・仮置き・別の推定）」に読み替える | **A:** 今のまま。仮置きも先に前提として承認する。**C:** 形式は今のまま、承認待ちの下書きにある前提を `check` で誤りにせず「承認待ち」と出す（下書きを 1 つずつ検査するという今の方針が崩れ、提案の承認も前提の承認を待つ） |
| 3 | 計画へ進む条件 | 上の確認の表をスキルに置き、エージェントが遷移の提案の根拠にする。`hitp` では止めない | `hitp` が確認の表を満たさない遷移を止める |
| 4 | 聞き方 | 1 回に 3 問まで。推定の幅を動かす順 | 数を決めない |
| 5 | 方向性の選択肢の示し方 | 方向性ごとに骨子の提案を出す（それぞれに推定を付ける）。リーダーは 1 つを承認し、ほかを却下する。新しい仕組みは要らない | 選択肢をまとめた 1 つの提案にする（選ぶ仕組みが要る） |
| 6 | 「磨く」の線引き | R1: 改善の提案は数字の食い違いか記録の欠けを根拠にし、良し悪しは述べない | — |
| 7 | 推定の一覧 | `status` に、記録にある推定の一覧（主題・値の幅・方法）を足す。前提の一覧と同じ理由 | `show` で 1 件ずつ見る |
| 8 | 企画書（文書）の扱い | 企画フェーズでは WorkItem を作らない。上長の承認などで企画書が要るなら、計画の最初の WorkItem（成果物: 企画書、ゲート: 上長の承認）として扱う | 企画フェーズでも成果物を出せるようにする |
