# hitp コマンドの仕様

記録を作る唯一の入口であり、エージェントが状態を読むための道具。
形式は `STORAGE.md`、不変条件は `DOMAIN-MODEL.md` に従う。

## 呼び方

```
hitp <command> [引数] [--json]
```

`hitp` は `node .claude/skills/hitp/scripts/hitp.mjs` のこと（APM で入れた場合）。プロジェクトのルートか、その下のディレクトリで実行する。
リーダーが短く打てるように、起動スクリプト `.claude/skills/hitp/scripts/hitp` を同梱している。PATH の通った場所に一度だけリンクを張る（`README.md`「使い方」）。

```
ln -s "$PWD/.claude/skills/hitp/scripts/hitp" ~/.local/bin/hitp
```

- リーダーは Claude Code の `!` で実行する（例: `! hitp approve PRP-0004 --expect 1a2b3c4d`）。
- `--json` を付けると、結果を JSON で標準出力に出す。エージェントはこちらを読む。
- 終了コード: `0` 成功、`1` 受け付けない（検査や不変条件に反した）、`2` 使い方の誤り。

## コマンド一覧

| コマンド | 種類 | 実行する人 | 何をするか |
|---|---|---|---|
| `init <名前>` | 書き込み | リーダー | `.hitp/` を作り、プロジェクトを始める（フェーズは企画） |
| `approve <ID> [--expect <ハッシュ>]` | 書き込み | リーダー | 下書き（`PRP`・`DRF`）を承認し、記録にする |
| `reject <ID> [--reason <理由>]` | 書き込み | リーダー | 提案（`PRP`）を却下する |
| `submit <WI> --file … --gate …` | 書き込み | リーダー | 成果物一式とゲート通過記録を提出する |
| `checkpoint <WI> <番号> [--date …] [--note …]` | 書き込み | リーダー | WorkItem のチェックポイントの通過を記録する |
| `status` | 読み取り | 誰でも | 現在の状態の要約 |
| `show <ID>` | 読み取り | 誰でも | 下書き・記録の中身 |
| `check [<ID>…]` | 読み取り | 誰でも | 下書きの検査 |
| `verify [--head <ハッシュ>]` | 読み取り | 誰でも | 記録と成果物の改ざん検査 |

hook は、エージェントが書き込み系のコマンドを呼ぶことを拒否する。

書き込み系は、受け付けたら最後に記録の末尾を出す（`記録の末尾: 12 番目 3f9a1c2b7d4e（あとで照らし合わせるとき: ! hitp verify --head 3f9a1c2b7d4e）`）。`--json` では `head: { seq, hash }`。リーダーが控えておくと、`verify --head` で記録が作り直されていないかを照らし合わせられる。受け付けなかったときは出さない（記録は増えていない）。

## 書き込み系

### `init <名前>`

- `.hitp/drafts/`・`.hitp/records/`・`.hitp/deliverables/` を作り、`initialized` イベントを書く。
- すでに記録があれば受け付けない。

### `approve <ID> [--expect <ハッシュ>]`

下書きを検査し、承認した結果を先に計算してから、`approved` イベントを書く。成功したら下書きのファイルを消す。

`--expect` には、読んだときの中身のハッシュの先頭（6 文字以上。`check`・`status`・`show` が 8 文字で出す）を渡す。ハッシュは、下書きと、それが辿る推定（記録にあるものは記録の中身、下書きのものは下書きの中身）をまとめた sha256。今の中身と合わなければ、何も書かずに止まる（終了コード 1）。リーダーが読んだあとに、エージェントが下書きや推定を書き換えた場合に気づくため（INV-1）。同じ推定を参照する別の提案を先に承認しても、ハッシュは変わらない。`--expect` を省くと今までどおり確かめずに承認する。
書き込み系のコマンド（`approve`・`reject`・`submit`・`checkpoint`）は、記録の末尾が `records/HEAD` と一致しなければ何もせずに止まる。

受け付けない場合:

- 下書きが形式に合わない、または未知の項目を持つ。
- 提案（`PRP`）の `rationale.refs` が空（INV-7）。
- 参照（`refs`、`assignee`、`estimate`、`dependsOn`、`tests` など）が解決できない。
- `add` の ID が既存の記録と重なる（削除・廃止したものも含む）。`update` の ID が無い、または削除・廃止している。
- 承認した結果が不変条件に反する。種類ごとの主な検査:

| `kind` | 検査 |
|---|---|
| `premises` | 削除する前提を、未完了の WorkItem の `tests` が参照していない |
| `assumption-status` | 対象が種類「仮定」の前提である |
| `plan` | 未完了の WorkItem をすべて含むか、含まないものは中止になる。完了・中止した WorkItem を含まない。依存に循環がない。探索型は `question` を持ち、`tests` は仮定を指す。承認済みゲートが付いた WorkItem から成果物の種類を消さない（INV-13） |
| `quality` | ゲートは、成果物を生む未完了の WorkItem にだけ付く（INV-13） |
| `phase` | 次のフェーズか、前のフェーズへの戻りである。終了したら変えられない（INV-11） |
| `cancel` | 対象が未完了の WorkItem である。ほかの未完了の WorkItem が依存していない（依存しているなら、先に計画を直す） |
| `progress` | 対象が未完了の WorkItem である。未着手なら進行中にする |
| `completion` | 対象が、成果物を生まない未完了の WorkItem である（INV-10・INV-14） |

### `reject <ID> [--reason <理由>]`

- 提案（`PRP`）だけが対象。却下した決定（`DEC`）を記録し、下書きを消す。
- 記録の下書き（`DRF`）が違っていたら、却下ではなくエージェントに直させる。

### `submit <WI> --file <種類>=<パス> … --gate id=<GATE>,by=<誰が>,at=<いつ>,result=<pass|fail> …`

例:

```
hitp submit WI-0003 \
  --file 検証報告=reports/api-latency.pdf \
  --gate id=GATE-0001,by=部長,at=2026-11-20,result=pass
```

受け付けない場合（不足を一覧にして示し、何も保存しない — INV-15）:

- WorkItem が現在の計画にない、完了・中止している（INV-12）、成果物を生まない（INV-14）。
- WorkItem が宣言した成果物の種類のうち、`--file` で渡されていないものがある。宣言していない種類がある。ファイルが無い。
- WorkItem に付いた承認済みゲートのうち、`--gate` が無いもの、または `result=fail` のものがある（INV-4）。
- WorkItem に付いていないゲートの `--gate` がある。同じゲートが 2 回ある。
- `by` が空、`at` が日付（`YYYY-MM-DD`）か日時（ISO 8601）でない。

成功したら、ファイルを `deliverables/<WI>/<種類>/` にコピーし、`submitted` イベントを書き、WorkItem を完了にする（INV-10）。

### `checkpoint <WI> <番号> [--date <YYYY-MM-DD>] [--note <ひとこと>]`

例:

```
hitp checkpoint WI-0003 2
hitp checkpoint WI-0003 2 --date 2026-11-09 --note "FAX の分は来週"
```

WorkItem のチェックポイント（計画で決めたもの。1 から数える）を通過したことを記録する。ゲートの通過記録と同じく、決まった形の記録なので、エージェントの下書きを通さずにリーダーが直接入れる。進捗報告（`RPT`）を 1 つ作り、本文は「チェックポイント 2「…」を通過」、残りの工数は計画のチェックポイントの値になる。日付を省くと今日。未着手の WorkItem は進行中になる。チェックポイントを通過しても、WorkItem は完了にならない（INV-10・INV-14）。

## 読み取り系

### `status`

表示するもの:

- プロジェクト名とフェーズ。
- 企画の骨子（問題意識・方向性・範囲）。
- 進捗の 3 軸: 作業進捗（状態ごとの WorkItem 数と残りの推定）、成果達成度（目的ごとの達成状況）、不確実性の解消度（仮定の検証状態ごとの数）。
- 前提の一覧（制約か仮定か、仮定なら検証状態とその覚え書き）。削除した前提は出さない。
- 記録にある推定の一覧（方法・主題・値の幅）。下書きにあるだけの推定は「未処理の下書き」に出る。
- メンバーの一覧（役割、週の稼働日、不在の期間、リーダーの言葉での稼働と能力の想定）。
- WorkItem の一覧（状態、担当、工数の幅、待ちの営業日、依存先、成果物の種類、付いているゲート）。チェックポイントがあれば何個目まで通過したかと次のもの、進行中なら最新の残りと最後の報告からの営業日。
- 見直しが要るもの: 未完了の WorkItem のうち、棄却された仮定を確かめた探索型の WorkItem に（たどって）依存するもの。
- 最近の進捗報告と不測の事態（新しい順に 5 件まで）。
- 計画の見通し（下記）。
- 未処理の下書きの一覧。問題の無い提案・記録の下書きには、承認するときのコマンド（`--expect` 付き）を添える。
- `--json` のときは、接頭辞ごとの次に使える ID（`nextIds`）も出す。

### `show <ID>`

下書き（`PRP`・`DRF`・`EST`）か、記録にある概念（`DEC`・`WI`・`GATE` など）の中身を表示する。
計画の下書きなら承認したときの見通しを、今の計画（`PLAN`）なら今の見通しを添える。`--capacity MEM-0002=3`（繰り返せる）で、メンバーの週の稼働日を仮に置き換えて見通しを出す。記録は変えない。稼働を変える修正案（メンバーの提案と組になる案）を、承認前に比べるため。
提案・記録の下書きには、中身のハッシュの先頭と、参照している推定の ID と、承認するときのコマンド（`--expect` 付き）を添える。

### `check [<ID>…]`

`approve` と同じ検査を、記録を書かずに行う。ID を省くとすべての下書きを検査する。推定（`EST`）には INV-6 を検査する。
未承認の下書きどうしが同じ ID を新しく作ろうとしていれば、両方に問題として出す（同じ計画を置き換える計画の下書きどうしは除く）。
参照が見つからない問題があっても、提案の中身と不変条件の問題まで一度に出す。
計画の下書きには、承認したときの見通しを添える（下書きを書いたときに hook が返す結果にも入る）。メンバーの提案（稼働・不在）と進捗報告の下書き（残り・チェックポイント）には、承認したときの今の計画の見通しを添える。計画が参照する ID（担当・根拠・検証する前提）を新しく作る、承認待ちのメンバー・前提の提案があれば、それらも番号の順に承認したとして計算し、そのことを示す。最初の計画では、メンバー・前提・計画が同時に承認待ちになるため。
問題の無い提案・記録の下書きには、承認するときのコマンド（`--expect` 付き）を添える。
1 つでも問題があれば終了コード `1`。エージェントは下書きを書いたら必ず実行する。

### 計画の見通し

`hitp` が決まった手順で計算する（`lib/forecast.mjs`）。数字だけを出し、無理かどうかは書かない。

- 完了見込み: 依存の鎖をたどって、すべての WorkItem が終わるまでの営業日（下限〜上限）。期限までの営業日と、超える日数。
- 人ごとの負荷: 担当する未完了の WorkItem の工数の合計と、期限までの稼働（営業日 × 週の稼働日 ÷ 5）。
- 見通しに入っていないもの: 担当・週の稼働日・工数の推定が無い WorkItem。

計算の約束: 平日だけ数え、祝日・年末年始は数えない。担当者は計画に並んだ順（依存先が先）に 1 つずつ進める。期間 = 工数 ÷ 週の稼働日 × 5 + 待ちの営業日。待ちは作業のあとに来て、その間、担当者はほかの WorkItem を進められる（負荷にも入らない）。担当も工数も無く待ちだけの WorkItem は、待ちだけを数える。完了した WorkItem は 0、中止した WorkItem は数えない。進行中の WorkItem は、残りの工数が書かれた最新の報告の残りで数える（無ければ推定の全量）。担当者の不在の営業日は、その担当者の作業を進めず、稼働からも除く。今日（`HITP_NOW` か、実行した機械の日付）から期限の日までを、両端を含めて数える。

### `verify [--head <ハッシュ>]`

- ハッシュ連鎖が切れていない。
- 記録の末尾が `records/HEAD` と一致する。
- 先頭から畳み込んで、すべてのイベントが受け付けられる。
- `deliverables/` のファイルが、記録した sha256 と一致する。記録にないファイルが無い。
- `--head` を付けると、書き込み系のあとに出た記録の末尾（ハッシュの先頭。16 進 8 文字以上）が、壊れていない連鎖の中にあるかも確かめる。無ければ、記録が作り直されたか、控えた値が違う（終了コード 1）。あれば、それが今の末尾か、そのあとにどの記録があるか（何番目・種類・対象・時刻）を出す。そのあとの記録がリーダーの書き込んだものかは、リーダーが確かめる。
- 連鎖と `records/HEAD` をまとめて作り直されると、`--head` なしでは分からない（ハッシュの計算は誰にでもできる）。リーダーの画面に出た末尾は、エージェントには書き換えられない。

## 不変条件と検査の対応

| 不変条件 | どこで守るか |
|---|---|
| INV-1 記録はリーダーの入力からだけ | 書き込み系（`checkpoint` を含む）は hitp だけ。hook がエージェントの呼び出しと保護領域への書き込みを拒否。`verify` が改ざんを検知 |
| INV-2 制約は決定なしに変わらない | 前提を変えられるのは `premises` の承認だけ。ほかの種類の `payload` は未知の項目を拒否 |
| INV-3 未承認の品質目標・ゲートは効力なし | 提出時の検査は記録にある承認済み・未廃止のゲートだけを見る |
| INV-4 ゲート充足の定義 | `submit` |
| INV-5 ハーネスは WorkItem を完了にしない | 完了にできるのは `submit` と `completion` の承認だけ。下書きは状態を書けない |
| INV-6 推定は導出を持つ | `check`・`approve` |
| INV-7 提案は根拠を持つ | `check`・`approve` |
| INV-8 メンバーへ直接連絡しない | 指示文だけ（hook では守らない） |
| INV-9 成果物の良し悪しを述べない | L3 の評価基準（hitp では守れない） |
| INV-10 成果物を生む WorkItem はゲート充足の提出でだけ完了 | `submit`・`completion` の検査 |
| INV-11 フェーズは決定なしに変わらない | `phase` の承認だけが変える |
| INV-12 提出は 1 回、成果物は変わらない | `submit`・`verify` |
| INV-13 ゲートは成果物を生む WorkItem にだけ | `quality`・`plan` の検査 |
| INV-14 成果物を生まない WorkItem は完了報告でだけ完了 | `completion`・`submit` の検査 |
| INV-15 不足のある提出は受け付けない | `submit` |

## 設計の判断

代案と比べて選んだもの。

1. **`reject` は提案だけを対象にする。** 記録の下書きが違っていたら、エージェントに直させる。
2. **フェーズは次への遷移と前への戻りだけを許し、終了したら変えられない。** フェーズによって使えるコマンドは制限しない。
3. **`approve --expect` は任意にする。**
4. **書き込み系は記録の末尾を出し、`verify --head` で照らし合わせる。** 代案だったのは、記録を git にコミットする（エージェントも履歴を書き換えられる）、末尾をプロジェクトの外に残す（同じ利用者なのでエージェントも書ける）。
5. **`submit` のゲート指定は `id=…,by=…,at=…,result=…` の形にする。** 名前に `,` や `=` を含められない。
6. **起動スクリプトを PATH の通った場所（`~/.local/bin` など）にリンクして使う。**
