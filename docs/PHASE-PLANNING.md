# 計画フェーズの振る舞い

計画フェーズで、エージェントが何をどの順で行い、何を記録に残すかの設計。
スキルは `.apm/skills/hitp-planning/SKILL.md`。

## 計画でやること

要件: 「企画を実現するためのスケジュールや人員計画を人間から情報を得ながら策定します。このフェーズでは、人間が『このぐらいの期限感でこのくらいの人員で各人の能力はこんなもんを想定している』というのをヒアリングした上で、プロジェクトの進行に無理ないかを判断し、無理がある場合は修正案を提案します」。

| | 中身 |
|---|---|
| 受け取るもの | 企画の記録（骨子・目的・前提・推定・効き目の順に並んだ未検証の仮定）と、リーダーの期限感・人員・各人の能力の想定 |
| 出すもの | メンバーの提案、WorkItem ごとの工数の推定、計画の提案、品質目標とゲートの提案、無理がないかの見通し、修正案 |
| しないこと | 期限や人員を無断で決める。人を評価する。成果物の良し悪しを述べる |

## 流れ

1. **聞く。** 期限感、人員、各人の稼働と能力の想定を聞く。1 回に 3 問まで、1 つの問いで聞くことは 1 つ（企画の R3 と同じ）。
2. **分ける。** 期限感を制約か仮定に分ける（「予算の締めに間に合わせたい」なら制約、「できれば」なら仮定）。メンバーの提案を書く。
3. **分ける（作業）。** 企画の目的を WorkItem に分ける。効き目の大きい未検証の仮定は、それを確かめる探索型の WorkItem にし、その仮定に依存する WorkItem の前に置く（`dependsOn`）。
4. **見積もる。** WorkItem ごとに工数を推定する。能力の想定（「新人」など）は、導出の係数として入れ、出どころを残す（例: 経験者なら 16〜24 人日 × 新人の係数 1.5〜2〈仮置き〉）。
5. **確かめる。** 計画の下書きの見通し（人ごとの負荷と、依存をたどった完了見込み）を `hitp` で出し、期限と比べる。
6. **直す。** 無理があれば、修正案を 2〜3 個出す。案ごとに見通しの数字を付ける。
7. **ゲートを付ける。** 成果物を生む WorkItem ごとに、品質目標とゲートを提案するか、ゲートを付けないことをリーダーに確かめる。
8. **引き継ぐ。** 下の「推進に進む前の確認」を根拠に、推進フェーズへの遷移を提案する。

## スキルに書く規則

| # | 規則 | 理由 |
|---|---|---|
| P1 | 期限の日付と稼働の数字は、リーダーの発言から取る。漠然とした期限感は、エージェントが日付を選ばずに仮定の前提にし、日付を聞く | PLAN §2「人員・期限を無断で確定」しない |
| P2 | 無理がないかは、`hitp` が出す見通しの数字で示す。「無理です」と言い切らず、「上限で期限を 18 営業日超える」と書く | LLM の暗算は外れる。例で、人ごとの負荷には余裕があるのに依存の鎖が期限を超えた。こういうずれは文章の計算では見落とす |
| P3 | 修正案は 2〜3 個。軸は期限・範囲・稼働・順序。案ごとに見通しの数字を付ける | 選ぶのはリーダー（企画の R6） |
| P4 | 制約に反する案（増やせない人員を増やすなど）は黙って出さない。出すなら、制約を変える前提の提案として明示する | INV-2 |
| P5 | 人を評価しない。能力の想定は、リーダーの言葉と推定の係数（仮置き）で扱う。「田中さんでは厳しい」と書かない | INV-9 は成果物についての規則だが、計画では人の評価に流れやすい |
| P6 | 仮定に依存する WorkItem の前に、その仮定を確かめる探索型の WorkItem を置く | R&D の軸。仮定が棄却されたら、推進で再計画の提案のきっかけになる |
| P7 | 成果物を生む WorkItem ごとに、ゲートを提案するか、付けないことをリーダーに確かめる | 品質目標とゲートはハーネスが提案し人間が承認する。黙ってゲート無しにしない |

## 例（2026-10-13 に、当時の `hitp` で通したもの）

企画の例（`PHASE-IDEATION.md`）の続き。企画では、制約「人員は 3 人（増やせない）」、仮定「期間は半年程度」「自動で読める割合は 50〜80%」、目的「手入力の時間を月 80 時間以上減らす」を承認して、計画フェーズに進んだ。今日は 2026-11-02。

リーダー（聞き取りへの答え）:
> 期限は 1 月末にしたい。年度の予算の締めに間に合わせたい。佐藤さんは業務に詳しくて専任。鈴木さんは OCR を触ったことがあるけど、ほかの案件と兼務で週 2 日。田中さんは新人で専任、プログラムは書ける。企画書は部長の承認が要る。

エージェントの下書き:

| 下書き | 中身 |
|---|---|
| メンバー | 佐藤（業務、専任）、鈴木（技術、兼務で週 2 日）、田中（実装、新人、専任） |
| 前提 | 制約: 1 月末までに試行運用を終える（予算の締め） |
| 工数の推定 | 企画書 2〜3 人日、読み取り率の検証 4〜8 人日、業務フローの整理 5〜8 人日、OCR 連携の実装 24〜48 人日（経験者 16〜24 × 新人の係数 1.5〜2、どちらも仮置き）、試行運用 10〜15 人日 |
| 計画 | 期限 2027-01-29。WI-0001 企画書（佐藤）、WI-0002 読み取り率の検証（探索、鈴木、仮定「自動で読める割合」を確かめる）、WI-0003 業務フロー（佐藤）、WI-0004 OCR 連携の実装（田中、WI-0002・0003 のあと）、WI-0005 試行運用（佐藤、WI-0004 のあと） |
| 品質目標とゲート | 検証に使う注文書は 200 枚以上。企画書は部長の承認、検証報告は課内の発表とフィードバック、連携プログラムは鈴木さんのコードレビュー |

見通し（手元のスクリプトで計算。平日だけ数え、担当者は計画の順に 1 つずつ進め、期間 = 工数 ÷ 週の稼働日 × 5）:

| 案 | 完了見込み | 期限まで | |
|---|---|---|---|
| 初版（期限 1/29） | 44〜83 営業日 | 65 営業日 | 上限で 18 営業日超える |
| 案 A: 期限を 2/26 に | 44〜83 営業日 | 85 営業日 | 収まる |
| 案 B: 鈴木さんを週 3 日に | 41〜76 営業日 | 65 営業日 | 上限で 11 営業日超える |
| 案 C: 範囲を PDF だけに（実装 16〜32 人日） | 36〜67 営業日 | 65 営業日 | 上限で 2 営業日超える |

人ごとの負荷（初版）: 佐藤 17〜26 人日／稼働 65 人日、鈴木 4〜8／26、田中 24〜48／65。**どの人にも余裕があるのに、依存の鎖（検証 → 実装 → 試行）が期限を超える。** 人が足りないのではなく、鈴木さんの週 2 日の検証を田中さんの実装が待つのが効いている。案 B が思ったほど効かず、案 C がほぼ収まるのも、表にしてはじめて分かる。

### 実際に通して分かった、当時の形式で足りなかったところ

1. **稼働が数字で残らない。** メンバーの稼働は文章（「兼務で週 2 日」）だけで、見通しの計算に使えない。
2. **見通しを出す仕組みが無い。** `hitp status` が出すのは残りの工数の合計（45〜82 人日）だけ。人ごとの負荷も、依存をたどった完了見込みも出ない。エージェントが文章で暗算することになる。
3. **工数の単位がそろう保証が無い。** 推定の単位は自由な文字列。「人日」と「時間」が混ざると、合計も見通しも出せない。
4. **最初の計画の修正案を並べられない。** 最初の計画では WorkItem がすべて新しいので、修正案の下書きを 2 つ並べると、同じ WI の ID を 2 つの下書きが作ることになり、`hitp check` が衝突として止める（5 件ずつ、計 10 件）。承認したあとの修正案は、WI が更新になるので並べられた。
5. **種類をまたぐ修正案を束ねられない。** 案 B は「メンバーの稼働の更新」で、案 A は「計画の置き換え」。両方を変える案は、提案 2 つを両方承認してもらうしかない。
6. **メンバーが `status` に出ない。** WorkItem の行に、工数の幅と依存先も出ない。
7. **ゲートの無い成果物が目立たない。** 例では業務フロー図と試行報告にゲートが無いが、どこにも出ない。

小さいこと: 下書きの検査が、根拠の参照が見つからないところで止まり、その先の問題（担当がメンバーにいない、など）を次の回まで出さなかった。一度に出すように直した。

## 推進に進む前の確認

エージェントは、遷移を提案するときにこの表を埋めて根拠にする。`hitp` は遷移を止めない。

| 確認 | どこで分かるか |
|---|---|
| 計画が承認されている | `hitp status` の計画 |
| すべての WorkItem に担当と工数の推定がある | `hitp status` の WorkItem |
| 見通しが期限に収まる。収まらないなら、修正案への回答が記録にある | `hitp status` の見通し、決定の記録 |
| 成果物を生む WorkItem に、ゲートが付いているか、付けないことが本文に書いてある | `hitp status` の WorkItem と、遷移の提案の本文（承認で記録に残る） |
| 仮定に依存する WorkItem の前に、それを確かめる探索型の WorkItem がある | `hitp status` の WorkItem |

## 決めたこと

2026-10-13 に、すべて推奨どおりで承認された（8 は書いたとおり）。

| # | 決めること | 推奨（採用） | 代案 |
|---|---|---|---|
| 1 | 稼働の数字 | メンバーに `capacity`（週あたりの稼働日。0〜5 の数）を足す。`ability`・`availability` はリーダーの言葉のまま残す。能力の想定は、推定の導出の係数として扱い、生産性の項目は作らない | 稼働も文章のまま。見通しはエージェントが計算する |
| 2 | 見通しの計算 | `hitp` が決まった手順で計算する。人ごとの負荷と稼働、依存をたどった完了見込みと期限までの営業日を、下限と上限で出す。計算の約束: 平日だけ数える、担当者は計画の順に 1 つずつ進める、期間 = 工数 ÷ 週の稼働日 × 5、今日（`HITP_NOW` か実行した日）から数える。祝日・年末年始は数えない（例の 65 営業日も年末年始を含んでいる）。数字だけを出し、無理かどうかは書かない。承認済みの計画は `status` に、計画の下書きは `check`（と `show`）に出す | エージェントが計算する |
| 3 | 工数の単位 | 計画の WorkItem が指す推定は、方法が工数見積（`effort`）で単位が「人日」のものに限る。`check` で止める | 単位を決めない（見通しは単位ごとに分かれる） |
| 4 | 修正案の並べ方 | 計画の提案に `replaces`（置き換える計画の ID。最初の計画は `null`）を足す。**承認できるのは、`replaces` が今の計画と一致するときだけ。** 同じ `replaces` の計画の下書きどうしは、同じ WorkItem の ID を作ってよい。1 つを承認すると、ほかは `replaces` が合わなくなって `check` が問題を出すので、リーダーが却下する。推進の再計画でも同じ仕組みが効く（古い計画をもとにした案を、うっかり承認しない） | 計画の下書きは 1 つだけ。修正案は助言の本文で比べ、選ばれた案に下書きを書き直す |
| 5 | 種類をまたぐ修正案 | 束ねる仕組みは作らない。別々の提案にし、本文で「案 B は PRP-0011 と PRP-0012 を両方承認する」と組を示す | 計画の提案に、メンバーの稼働の変更も入れられるようにする |
| 6 | `status` の表示 | メンバーの一覧（役割・稼働・能力の想定）と、計画の見通しを足す。WorkItem の行に、工数の幅と依存先を足す | — |
| 7 | 推進に進む条件とゲートの無い成果物 | 上の確認の表をスキルに置き、`hitp` では止めない。ゲートを付けない成果物は、遷移の提案の本文に書き、承認で記録に残す | ゲートを付けないことを記録する仕組みを作る |
| 8 | 規則 P1〜P7 | 上のとおり。特に P4（制約に反する案は前提の変更として明示）と P5（人を評価しない） | — |
| 9 | 待ち時間（試したあとに追加） | WorkItem に待ちの営業日（`waitDays`）を持たせる。見通しでは依存の鎖に足し、負荷には入れない。承認待ちにも外部の納品待ちにも使える | ゲートに「かかる営業日」を持たせる（ゲートと関係の無い待ちは表せない）。工数に足して代用する |
